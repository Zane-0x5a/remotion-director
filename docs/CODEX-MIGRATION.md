# remotion-director → Codex 移植分析

核对日期：2026-09-25。源码基线：`28fb82c`，与核对时远端 `master` 相同。

## 结论与范围

完整创作流程可以迁到本地 Codex。本分支已实现“可安装的插件 + 一个编排入口 + 四类原生子代理协议 + 现有渲染工具”，并实际安装、发现入口和渲染过独立工区 fixture。设计装备、盲选标准、甲乙环和节奏刀保留；宿主调用与交接由生成适配器和运行台账承载。完整创作链尚未通过验收，不能把安装和渲染成功等同于全功能移植完成。

本轮已从分析推进到实现与主代理审查。实施顺序见 [CODEX-MIGRATION-PLAN.md](CODEX-MIGRATION-PLAN.md)，实际证据与剩余发布阻塞项见 [CODEX-VALIDATION.md](CODEX-VALIDATION.md)。安装测试使用临时隔离配置，不替换用户的日常插件配置。

首个目标环境为本地 Codex 桌面端，CLI 作为第二验收目标。公开目录上架是单独的分发工作；插件依赖本机 Node、Chromium、ffmpeg 和文件读写，不能因打包成功就宣称同时支持所有 ChatGPT 表面。[S1][S2]

## 原始目的与必须保留的行为

依据 `docs/WHY.md`、`docs/DEVELOPMENT-JOURNEY.md` 和现有角色协议，移植必须保护：

- 乙在同一个代理上下文中完成设计、施工、自检和后续修复，不能拆成设计者交稿给另一位工程师。
- N 个独立执行先各自定稿，再由看不到作者来历的 selector 挑潜力最大的基底。
- 甲只依据 brief 与像素判断；同一只甲跨轮保留自己的评审记忆，主代理逐字摆渡判词与反驳。
- 三步装备加载顺序、§4 自检人格、held/mid 语义、原生分辨率裁切和用户肉眼终审均保留。
- 节奏刀是新上下文，读取真实源码时间数据，仅改变时间；用户确定的总时长保持锁定。
- 工程版本追上游；设计方法和创作选择不因引擎版本策略被限制。RBP 优先更新已有全局安装。

要避免的假完成：能显示技能、能启动子代理或能出 MP4，但乙被换人、甲读过设计、旧帧被当成新帧、只读了缩略图，或最终展示的不是实际受评与重渲的版本。

## 推荐的 Codex 结构

### 1. 对外一个明确入口，内部按角色加载

建议对外入口使用 `remotion-director`，保留现有三个技能的全部流程，但将 `design-brain`、`critic-loop` 作为入口下按角色加载的内部资料。四份角色正文也作为随包参考资料，主代理启动原生子代理时提供对应角色正文或准确的加载入口。

这样不要求用户修改全局 `.codex/agents`，也避免一个通用的 `create` 或 `design-brain` 在无关会话中抢先激活。若需要保留独立内部技能，其隐式调用应关闭，且依然要审计盲评上下文。

安装文件树应自包含：角色、七份设计轴、两个评审协议、五个运行脚本及依赖默认值都随包交付。安装后从新工区运行，不得回读开发仓库里的脚本。

### 2. 共用内容源，分离宿主适配

短期保留根目录现有 Claude 源码作为权威，通过 Codex 适配生成分发包；不手工维护第三套设计知识。现有 DSH 文件仍由其自己的适配负责。

允许的宿主变换：路径解析、shell 调用、角色启动/续话/返回方式、工具名称与技能发现配置。设计判准和评审正文其余部分逐字保持；交付句中的宿主用词作为明确列出的转换例外。

生成验证应覆盖角色、技能、工具与 manifest 的来源和输出，而不只给 `skills/` 做一个哈希。变换目标不存在、残留旧宿主调用或正文出现未许可差异时，生成直接失败。

### 3. 生命周期是主要适配工作

| 角色 | 首次进入 | 后续阶段 | 交付判据 |
| --- | --- | --- | --- |
| 主编排 | 用户 brief、参数、持续任务状态 | 负责调度与原文转交，不做美学裁决 | 核对完成报告与实际产物后推进流程 |
| builder × N | 独立新上下文；角色、装备入口、规格、自己的目录与 RBP 路径 | 胜者继续同一个代理，直至修复完成 | 明确 `settled` 或 `round done`，指明实际 canonical |
| blind-selector | 新上下文；brief、匿名候选图片、裁切目录 | 一次性选出潜力最大的基底 | 完整 `{ winner, reason }` |
| aesthetic-critic | 新上下文；甲的原文协议、brief、当前帧条 | 续话到同一个代理；只增加新帧、原文反驳及自己的既往判词 | 判词原文与 `CONVERGED: YES/NO`；输入错误不是收敛 |
| tempo-pass | 新上下文；时间判准、源码、设计、收敛版、时长授权 | 必要时继续该阶段；与 builder 错开写文件 | `done` 或 `blocked`，最终输出与时长变化 |

在 Codex 中，代理返回的最终消息也可以是明确交付；无需机械保留 Claude 的 `SendMessage`。但“回合结束”“idle”与“任务完成”仍然不同。续话必须使用实际宿主提供的恢复/后续任务操作；仅投递消息未必会启动空闲代理的新一轮。

持久代理是同一任务内的上下文连续性，不是保证应用重启后永不丢失上下文。恢复时先检查旧代理是否仍可续接；死亡后的读档救援仍按现有协议记录为降级，不能伪称保留了原始记忆。

具体调用参数由目标版本适配；不能把某一次会话提供的工具名称写成所有 Codex 客户端的永久 API。并行数、可保持的代理数量、图片输入能力也应在开工时检查，资源不足时不得静默降低用户选择的 N。

### 4. 盲评分成三个可验证问题

**上下文来源。** 启动 selector 和甲时不继承主代理对话，不包含 DESIGN、代码、自检辩护、候选作者和预期赢家。采用目标宿主实际提供的干净启动能力。全局指令和技能发现仍可能进入子代理，必须看实际行为记录。

**证据输入。** 给 selector 准备 A/B/C 匿名素材目录，编号映射只由主代理保存，避免直接路径 `draw-3` 暴露执行顺序。甲只接收该轮已核验的图片。若让甲自行读取合并的 `CRITIC-PROTOCOL.md`，还会读到乙的修复/救援段；应只注入甲方正文，或提供独立生成的甲方文本。

**实际访问。** 第一版可按现有产品的“提示词约束 + 干净上下文 + 访问记录核验”实现。现有 Claude 角色的 `Read`/`Bash` 也不是按文件划分的硬沙箱，不能把它描述成已有的强隔离保证。若验收观察到越界读设计，盲评仍属未完成，必须修复后再发布。需要结构性文件隔离时，再为评审提供独立环境与受限的读图/裁切能力；仅加一个 MCP 工具而保留任意 shell 并不能形成隔离。

### 5. 工程自动更新与创作流程分工

保留当前开工自动追 npm stable latest、RBP 全局优先更新、每次制作准备一次、制作中协调更新的策略。包中的精确依赖版本是构建/测试快照，不重新变成永久支持版本门槛。

本轮独立工区准备时解析的 npm stable latest 和上游 RBP 声明版本均为 4.0.529；已有全局 RBP 原位更新，第二次检查复用匹配文件，未另建工区副本。这是 2026-09-25 的运行观察，不是版本上限。RBP 的通用流程建议不接管已确定的 N 抽和甲乙环；Codex 入口明确任务包括成片、帧条和盲评。无需冻结 RBP 或改写其上游正文。

建议增加一个跨平台 Node 调用入口，由它设置 `NODE_PATH`、选择工区的 `tsx` 并调用现有 render 脚本。避免把 Bash 的前缀赋值机械放进 PowerShell。同时检验安装目录只读时的构建缓存位置，不能依赖开发仓库恰好有 `node_modules`。

### 6. 最小运行记录，保护连续交接

保存工区级运行记录，包含已确认的 commission、`locked/free`、实际环境、draw→代理标识、明确完成报告、canonical 路径、评审轮次与实际受评帧条。逐字判词独立存档。帧条模式、帧清单与视频对应关系由脚本核验。

canonical 仍只在“施工者明确报告完成 + 核验该版产物”后前移。读运行记录不是在磁盘上猜哪个目录最大，也不是用落盘文字替代活代理记忆。更高编号的失败目录、旧报告重送、过期判词均不能推进状态。

代码可以核验路径、状态和文件一致性；设计是否够好仍由正确上下文中的评审和用户判断。工程脚本不新增设计评分或替代甲方审美。

## 验收顺序

1. **先用已有渲染素材验证角色通信。** N 个完成报告、一次盲选、至少两轮甲乙续话、一次反驳、一次 tempo 交接。不要求为了测试强迫审美模型制造缺陷，可使用明确标注的控制流测试代理；这部分只验机制。
2. **验证分发与执行。** 新装到含空格/中文路径，在完全独立且空的制作工区启动；安装目录无 `node_modules` 且只读。确认所用脚本来自安装包，Windows 与 Bash 环境分别验命令入口。
3. **集中重放失败和边界。** 首轮 canonical 是 r3；磁盘有失败的 r4；回合结束但无完成报告；报告路径不存在；帧条和视频错配；缺图/坏图；判词格式不完整；旧报告重复送达；builder 死亡；global RBP 更新无写权限；网络断开；ffmpeg 只支持版本查询却不能抽帧。
4. **盲评实际验证。** 在主代理上下文和设计文件中放测试标记，审计 selector/甲的实际输入和读取；检查所有所需帧与 native crops 确实被打开。再使用已知 held 缺陷与 mid 瞬态素材验证判断边界。仅仅没在最终答案中出现标记不算未污染的充分证据。
5. **完整真实创作。** 先做一个全流程案例暴露接口问题，再覆盖至少两个不同 brief、locked/free 时长、N=1 与 N>1。验证胜者不换人、甲持续记忆、节奏刀不重设计、最终播放版本正确。用户审美验收通过，才称完整移植已完成。

原插件的音频仍是实验能力，横屏/方形及固定 9:16 分析栅格仍有现有验证边界。移植时原样标示；若要宣称这些方向也达到发布水准，需单独补验，不把它们随包装升级成已验证能力。

## 本轮实际验证与未决项

已核对上游基线、已合并修复、全部角色和关键协议、官方文档。实际安装使用桌面附带的 Codex CLI 0.155.0-alpha.16.4，避免了本机失效的旧 npm 包装器；从安装缓存运行的 fixture 已生成 1080×1920、30fps、6 秒视频、六张 still 和 punctuated strip。

真实夜班公交案例启动了两个独立 builder。draw-2 已交付视频、帧条与裁切；draw-1 的低权限渲染报 `uv_os_get_passwd ENOMEM`，高权限重试被自动审批拒绝。由于 N=2 尚未全部 settled，未进入盲选、持续甲乙和节奏刀，不得静默降为 N=1。

这些剩余项仍是完整迁移的发布阻塞项。该分支适合提交审查用 PR，不应标为完整创作能力已验收或自动合并。退出应用后的代理恢复、硬文件隔离和用户审美认可均未验证。
